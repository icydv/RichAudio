## Reviewed T0 scope, now consumed

The private candidate manifest binds the one literal supplied executable path, helper executable, output directory, attempt identity and measured runtime closure. Public documentation omits my personal directory. At preparation, source size, identity and complete-file SHA-256 were unknown. The first inspection recorded private size/identity and hashes of only its permitted ranges; the complete-file hash remains null. That observation cannot establish historical whole-binary integrity or authenticity.

The inspector opens only that source file for read access, with no-follow parent/file handles, one hard link required and write/delete sharing refused. It accepts a regular file of 512 bytes through 32 MiB. Its source read plan is conditional on validated metadata and has these hard bounds:

| Item | Allowed read |
| --- | --- |
| DOS header | Exactly 64 bytes at offset 0 |
| PE signature and COFF header | Exactly 24 bytes at validated `e_lfanew`, within the first 4,096 file bytes |
| Optional header and section headers | Exactly the declared optional header plus at most 32 section headers; this complete range must also fit within the first 4,096 bytes |
| Resource directory metadata | Three bounded directory headers and entry tables, following numeric type `RT_VERSION` (16), unique numeric version name 1 and one numeric language; at most 32 entries in the root and one entry at each selected lower level |
| Version data entry | Exactly 16 bytes at the validated resource-relative offset |
| Version resource payload | Only the selected `RT_VERSION` payload, 92 through 16,384 bytes |
| Total source IO | At most 65,536 requested bytes and 16 direct `ReadFile` calls; the supported success path uses 11 calls |

The 4,096-byte header bound is a location ceiling, not permission to read a blind prefix. The inspector skips the DOS stub and does not read section code, CLR/IL metadata, imports, certificates, manifests, icons, other resource payloads or embedded assets. It validates PE32/PE32+ layout, complete section headers, unique file-backed RVA mapping, section bounds and overlap, resource-relative bounds, and the version structure's lengths, alignment, fixed signature and bounded Unicode fields. Unsupported layouts, multiple version names/languages, malformed pointers, missing version information or a short read stop the attempt. There is no fallback to Windows version APIs, a general PE library or a larger read.

The private result contains observed machine/header values, fixed file/product version numbers, at most seven bounded version strings, source identity, per-range offset/count/hash and the version payload hash. It stores no raw header, source code or resource payload. Version strings are declarations inside an untrusted file. They do not prove the folder's advertised version, release provenance, licensing permission, genuine Enhanced support or correctness of future game-resource exports. The whole-binary hash remains null. A malicious executable can mislabel bytes as a version resource; structural qualification identifies the permitted branch, not the historical truth of its contents.

## Execution and evidence boundary

The new helper executes its own fixed inspector code in a separate child process. It never executes, loads as a module/assembly, disassembles or imports code from my supplied executable. A parent-controlled gate remains closed until the child is assigned to a Windows Job with one active process, 128 MiB process memory and kill-on-close. The fixed helper has no networking, game, key-loading, UI or audio API. This is reviewed code-level restriction, not a claim that the inspector runs in an OS network sandbox.

The worker deadline is five seconds. Failure terminates the Job and verifies the child joins within a further five seconds; an unassigned child is killed directly and joined. Separate byte pumps drain stdout and stderr concurrently, capped at 4,098 bytes (4 KiB JSON plus newline) and 4,096 bytes. Their verified joins share a further five-second budget. Both sides use explicit UTF-8; the private JSON output omits the transport newline and remains at most 4 KiB. The executable source, compiler, helper, manifest, preparer and tests receive hash bindings. Preparation rejects CLR override names before starting the compiler or helper, then records the actual loaded managed/runtime module files plus `machine.config`; execution rejects loaded/pinned-file drift, an executable `.config`, and CLR injection/override environment variables. The child receives a cleared environment containing only required Windows directory variables. Windows and the already running PowerShell/control account remain trusted; this is not a complete OS closure or qualification for arbitrary hostile native parsers.

Only fixed private candidate inputs, the exact measured runtime files and the one approved source are readable by this procedure. Source-parent metadata is inspected through held handles without directory enumeration. Private output parents are pinned, receipts use create-new writes and bounded output, and existing result/consumed files are refused.
