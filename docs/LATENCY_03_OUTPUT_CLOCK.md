# LATENCY-03: isolated output and observed device-clock preparation

I have a buildable, isolated synthetic output route using the existing `WasapiOutput` implementation. Codex prepared it offline; **no real endpoint was enumerated, activated, queried or played**. The ordinary constructor, gameplay selection, 48 kHz stereo Float32 route, saved preferences and literal-null gameplay event bus remain in place. The new factory is not called by `HostProgram`.

`WasapiOutput.CreateSyntheticExperiment(ring, session)` claims one fresh `Latency03OutputSession`. The session requires an exact endpoint identity, eight prewarmed original kernels, a declared gain and finite duration. A presealed authored-clock bus, missing kernels or a second factory claim is rejected before endpoint access. Factory construction alone creates no endpoint; only a future explicitly authorized `Start` enters Core Audio.

## Shared-mode capabilities

The first proposed device session selects `requestedPeriodFrames=0`: if available, `IAudioClient3` is queried for capabilities, but initialization still uses the existing shared `IAudioClient.Initialize` request. No smaller period is selected automatically. An unavailable interface is recorded; a failed capability query on an available interface ends the attempt. An explicitly requested nonzero period has a separate supported-API branch, with no rounding, substitution or fallback after failure. That branch is available for later separately reviewed experiments, not selected by this first proposal.

The declared `IAudioClient3` ABI includes the complete inherited `IAudioClient` and `IAudioClient2` vtable. Codex compared it with the [official Microsoft header](https://github.com/microsoft/win32metadata/blob/64ed9177fb76eb244fc9051c74b8a93fdfe20873/generation/WinSDK/RecompiledIdlHeaders/um/Audioclient.h), whose retained SHA-256 is `f0ddbd205f63352f5f1d04e429f7a168ebebfbebe5e879c36c876ac7ec520df2`. These are declarations and managed fake tests, not evidence that my selected endpoint implements the interface.

Microsoft specifies that [`GetSharedModeEnginePeriod`](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-getsharedmodeengineperiod) returns format/client-dependent default, fundamental, minimum and maximum periods. A request must be an integer multiple of the fundamental within the returned range. The minimum is not assumed to equal the fundamental. [`InitializeSharedAudioStream`](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-initializesharedaudiostream) computes its buffer from the requested period, supports event notification and can reject the request. The code does not require exclusive ownership or change client category/offload properties.

[`GetCurrentSharedModeEnginePeriod`](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-getcurrentsharedmodeengineperiod) is an instantaneous observation that another client can invalidate. Its period/format and HRESULT are retained; the allocated format is freed outside the callback. An endpoint period cannot be inferred from a nominal buffer request or Windows version. Actual buffer size, padding, wake intervals, stream latency and MMCSS registration/revert results remain separate observations.

## Actual clock observations rather than an invented epoch

[`IAudioClock.GetPosition`](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition) provides a stream-relative device position and its correlated QPC timestamp. Position units require the separately queried frequency; the offset in seconds is `position / frequency`. The returned QPC uses 100 ns units, rather than raw `Stopwatch` ticks. A fresh stream begins at position zero, which may initially remain frozen while output starts. `S_FALSE` does not establish an accurate observation; this first candidate stops instead of retrying it into a passing result.

The new clock qualifies only after two arrived, positive, advancing `S_OK` observations. Its frame model converts actual device units using the returned frequency. It interpolates an event time only between arrived clock observations; it does not extrapolate a pose or future device-clock history. Monotonicity, bounded query duration/age and consistency with measured query/quantization brackets are checked. A valid query need not have a zero-width timing bracket, and an API stream-position model remains distinct from measured physical speaker output.

For a bracketed event, conservative mapping uncertainty includes query duration, device-position quantization, QPC conversion and the event's declared uncertainty. The mapped upper frame is rounded conservatively. This is the explicit software clock model under test, not a recovered driver error specification or a promise of sample-accurate acoustic arrival.

An event newer than the latest arrived clock observation waits as a descriptor until a later callback supplies its bracket. This can add a scheduling opportunity; it is not hidden in a claimed latency saving. The event occurrence stays unchanged. The two descriptor lanes and waiting storage share a global 128-event budget, alongside the existing 32 active voices. There is no new continuous PCM queue. Deferred qualification rechecks both original 250 ms occurrence and observation freshness gates; unsupported history or expired events are rejected, not relabelled.

The clock retains at most 128 observations for bounded lookup. The 2 ms query-duration and 100 ms clock-age/freeze limits are explicit experimental admission gates, not observed endpoint capabilities. An old event outside retained clock history remains unavailable even if another freshness check would allow it.

## Writable frames and submission evidence

The ingress receipt retains an **acknowledged frontier lower bound** and the currently reserved-through frontier. They are not an atomic statement that every frame between them remains writable: an event arriving before dequeue may enter the current owned packet, while one arriving after dequeue waits. Consumer admission records the actual owned packet's first writable frame.

The original event kernel already contains direct and reflected acoustic travel times. The integer direct-onset guard, clock uncertainty and any explicit common software lateness shift the whole kernel; reflected delays are not added again or moved independently. Samples already released to WASAPI are never edited.

The isolated route records separate acquisition, fill and [`ReleaseBuffer`](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiorenderclient-releasebuffer) brackets. Only a successful ordinary release acknowledges an event's first submitted sample. Every successful acquire has exactly one release attempt: an unexpected fill/mapping exception releases that packet as `SILENT`, records the fault and never acknowledges its event. Joined control cleanup also retires descriptors interrupted after dequeue. Failed acquisition/release, continuous starvation or a bus fault ends the attempt. An underflow cannot be concealed by an event. The pre-existing gameplay fill remains the literal-null event route.

After output joins, retained device-clock positions can bracket the crossing of a submitted first-output frame. This is available endpoint presentation-clock evidence. It is not a microphone capture, waveform correlation or physical input-to-ear measurement; downstream behavior and driver accuracy remain unverified. The approximately 15.5 ms LATENCY-02 fake-submission median is a comparison question for the future experiment, not a result of this implementation.

## Bounded callback and cleanup behavior

Clock, callback and submission rows are preallocated, each with a 30,000-row cap. Critical application helpers have no allocation opcodes, source loading, file IO, geometry work, logging or worker waits. Full callback costs and optional per-thread managed-allocation deltas are retained; an unavailable counter is `-1`, not an invented zero. Managed fake tests do not establish that real COM/driver execution allocates nothing or meets a deadline.

The ordinary MMCSS `Audio` task is retained. Stop closes admission and requests retirement. Completion separately requires joined output/ingress lifetimes, successful applicable Stop/Reset results and off-callback queue/voice drain. A requested stop, written stop file or callback return is not completed silence. The independent process supervisor and its hard lifetime bound belong to the separately reviewed experiment launcher.

The optional `ProtectActiveTails03` burst policy is intentionally different from the LATENCY-02 default: it rejects an incoming event rather than hard-stealing an active tail. This preserves continuous PCM and existing event tails at the cost of new-onset admission. It introduces no extra voices, arbitrary crossfade, limiter or calibration change. Root-level burst fixtures/reporting compare that trade-off; the original default policy is preserved.
