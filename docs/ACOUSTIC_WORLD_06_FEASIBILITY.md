# ACOUSTIC-WORLD-06: installation-wide static preparation feasibility

I want my supported static acoustic world prepared before normal gameplay, including places I have never visited. Nearby tile loading is a runtime selection policy, not a discovery policy. Codex researched public source and documentation for this increment; it did not inspect my installation, tools, previous private captures, SDK binaries or keys.

The practical architecture is **headless static discovery and decoding, followed by runtime state validation**. Public development source demonstrates that archived map/collision resources can be indexed and decoded without moving the player. It does not establish a supported, redistributable, complete GTA V Enhanced reader for my installation. I cannot presently name a qualified public RPH/Enhanced API that returns the complete effective world inventory and all unstreamed collision triangles. The next real experiment therefore needs a legitimate metadata/archive provider and a bounded broad inventory, rather than another one-building export or a camera tour.

An interior proxy is not a validated MLO room/portal graph; those relationships need their actual supported resources. An AABB is useful for scheduling and missing-coverage envelopes; it is not a reflective façade. File hashes and directory entries are not geometry either.

## Effective world selection needs more than a DLC list

The reference reads the update archive's `dlclist.xml`, applies patched paths, reads each setup file's device/content declarations and sorts setup records by their declared order. Content records include enable/disable changesets, overlays and extra mounts. DLC cache names are derived from cache-enabled changesets. Consequently, DLC-list order, alphabetical directories and matching basenames cannot independently establish effective precedence. See [setup fields](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/FileTypes/DlcSetupFile.cs#L10-L37) and [content/changeset fields](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/FileTypes/DlcContentFile.cs#L188-L202).

My discovery model needs the physical archive/member identity, effective logical mount path, override chain, platform/build variant, dependency ownership and activation conditions. It must preserve hash collisions and unresolved associations. Custom loaders can introduce mounts outside the declared base/DLC model; an unrepresented custom root remains outside known coverage. Static alternatives for supported IPL/interior/time/weather states should be cached before play and selected later from qualified runtime state. Merely processing the currently active subset would repeat the exploration-dependent mistake.

The public reference is not itself a sealed acquisition procedure: [RpfManager.Init](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/RpfManager.cs#L35-L45) can recursively enumerate archives and uses a process-global Gen9 setting. It also contains an [explicit DLC exception whose cause is marked unresolved](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/GameFileCache.cs#L606-L610). A normal GameFileCache/Space or GUI startup can read additional resources. My production design needs a constrained headless reader, explicit mount/provider contracts and separately qualified process containment, not an unrestricted call to those entry points or a claim that this tool's selected dictionary is GTA's observed runtime world.

## Comparing the acquisition routes

| Route | Assessment for my Story Mode/RPH product |
| --- | --- |
| Supported complete index and geometry provider | Preferred if a legitimate Enhanced-capable provider exposes complete effective inventories and bounded geometry reads. No such qualified provider has been established here. Provider identity, redistribution/use terms, archive/decryption capability and real resource evidence are prerequisites. |
| Existing GTA/RPH streaming interfaces alone | Insufficient evidence for complete static prewarming. RPH's documented [Model.IsCollisionLoaded](https://docs.ragepluginhook.net/html/P_Rage_Model_IsCollisionLoaded.htm) reports residency, not triangles or a complete inventory. It applies to an old API version. Loaded entities and ray observations cannot stand in for every unvisited static resource. |
| Streaming requests or scene sweeps | The community-maintained [collision request](https://github.com/citizenfx/natives/blob/c00e0ed83d06dcba2457424ba254fbaa7a05bf7e/STREAMING/RequestCollisionAtCoord.md) and [scene-sphere request](https://github.com/citizenfx/natives/blob/c00e0ed83d06dcba2457424ba254fbaa7a05bf7e/STREAMING/NewLoadSceneStartSphere.md) describe coordinate-bounded streaming operations. They do not enumerate every asset or return collision triangles. Forcing global streaming changes engine state, has unqualified memory/lifetime effects and would not satisfy my read-only static acquisition requirement. CitizenFX documentation is not an RPH Enhanced support guarantee. |
| Static decoding plus runtime validation | Recommended engineering route. Discover and prepare the whole qualified static domain outside gameplay/audio callbacks; persist bounded tiles and dependency indexes; validate activation and dynamic state later. Runtime rays remain checks or dynamic evidence, without becoming the source of basic world coverage. |

I credit **dexyfex / CodeWalker** as a development reference and link the [author's distribution page](https://www.gta5-mods.com/tools/codewalker-gtav-interactive-3d-map?amp=1). CodeWalker's [source notice](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/Readme_Src.txt) restricts that source release to educational use. It is not a blanket redistributable implementation licence. My public product needs a legitimately usable reader/provider and resolved component terms; a development GUI or educational reference cannot silently become a runtime dependency. Private Enhanced decryption data has not been supplied or authorized. No key extraction, embedded-key acquisition or assumed Legacy/Gen9 interchangeability is proposed.

## Earliest startup and loading UI

The repository's [historical startup hook](STARTUP_WORLD_WARMUP_01.md) compiled and queued preparation at plugin entry, but did not establish when that entry occurs relative to native loading or player control. Preserved records refer to Enhanced `1.0.1158.16` and RPH `1.132.1428.17748`; they are historical bindings, not a current installation check or loading-screen API qualification.

The official historical [IsLoading contract](https://docs.ragepluginhook.net/html/P_Rage_Game_IsLoading.htm) is a getter. It does not authorize holding the native screen or replacing its `Loading Story Mode` label. The documented [FrameRender/RawFrameRender distinction](https://docs.ragepluginhook.net/html/Events_T_Rage_Game.htm) also matters: native calls are explicitly unsafe in the raw-frame callback. Those public pages identify the older 0.56 API, and some direct requests failed during research. Their limits do not prove that a newer supported API is absent; the exact Enhanced/RPH contract remains unverified.

CitizenFX's pinned [busy-spinner text](https://github.com/citizenfx/natives/blob/c00e0ed83d06dcba2457424ba254fbaa7a05bf7e/HUD/BeginTextCommandBusyspinnerOn.md) and [spinner type](https://github.com/citizenfx/natives/blob/c00e0ed83d06dcba2457424ba254fbaa7a05bf7e/HUD/EndTextCommandBusyspinnerOn.md) describe a loading prompt, including a right-side spinner. They do not establish a safe replacement of GTA's existing Story Mode message, availability before plugin entry, or support on my target. I will not implement a memory patch, busy-loop native gate, forced fade/pause or loading-screen hold from those names.

My fallback is a RichAudio-owned readiness view showing **“Warming up acoustic cache — XX%”** at the bottom right, with a normal responsive progress panel. An owned prelaunch host is the earliest stage I can control independently of GTA; integrating it into my normal launch route still needs implementation and validation. A plugin-owned post-initialisation view is another future option after its actual callbacks and cancellation behaviour are qualified. Neither currently proves that GTA player control is held until ready. The offline coordinator can gate **RichAudio acoustic readiness** now; a native player-control gate remains separate and unimplemented.

Discovery begins indeterminate. After a closed inventory fixes the workload, the implemented percentage counts verified, persisted eligible tiles; stage labels describe input/conversion work and cache verification, with cache hits recorded separately. It is not an estimate of elapsed time or three separately weighted processing counters. “100% processed” always names its denominator. Unknown roots, unsupported assets, conditional states, internal geometry gaps and failed tasks remain separate from complete supported coverage. The final view offers recovery or explicit partial continuation rather than a false “world ready”. Tiles and compact indexes remain on disk, with nearby completed tiles and relevant corridors paged into bounded memory after preparation.

The new offline startup work tests this architecture with original full-domain fixtures. It is not installed-world discovery, a timing estimate, an approved startup hook or genuine interior coverage. The [next access proposal](ACOUSTIC_WORLD_06_READ_ONLY_PROPOSAL.md) tests broad inventory viability and dependency closure, with the missing real inputs and approval boundary explicit.
