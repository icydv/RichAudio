## The actual missing dependency

The headless API is `GTA5Keys.LoadFromPath(path, gen9: true, key: null)`. It searches `gta5_enhanced.exe` for AES, then initializes NG using `Resources.magic`. Its optional base64 `key` skips the executable read, but still needs that payload. Expanded-key-file loading is commented out; GUI operation and manual expanded-state export are unnecessary. [GTAKeys.cs, lines 156–179 and 248–314](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/Utils/GTAKeys.cs#L156-L179)

My missing genuine dependency is a compatible opaque payload **and matching AES capability** (32 bytes), or approved executable bytes supplying AES. The expanded layout is 306,272 bytes: schedules 27,472, decryption tables 278,528, filename-hash LUT 256, AWC 16. My WORLD08 NG-only state omits AWC: 306,256 bytes. AES alone is insufficient. [GTAKeys.cs, lines 296–314](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/Utils/GTAKeys.cs#L296-L314)

My WORLD08 build deliberately replaces implicit `LoadFromPath` initialization and the embedded-resource getter with exceptions. Re-enabling the former would neither provide the omitted payload nor respect my explicit input boundary. The upstream getter requests a managed byte-array resource named `magic`. ## NG, Gen9 and runtime dependencies are separate

NG is archive/member encryption. The 256-byte `PC_LUT` used by `GTA5Hash` participates in filename hashing; it is not a Gen9 material conversion table. NG decryption requires the schedules and decryption tables. AES-encrypted directories/members instead use the AES capability. The key selector combines the filename hash and declared length; successful byte decompression does not authenticate a source. [GTACrypto.cs, lines 33–59 and 96–155](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/Utils/GTACrypto.cs#L96-L155)

Gen9 resource layout selection is `RpfManager.IsGen9`, copied into each `ResourceDataReader`. It supplies no encryption state. I retain serialized selection and restoration around my offline reader. I do not call `RpfManager.Init(folder, ...)`, whose normal implementation recursively discovers RPFs and scans them. [ResourceData.cs, lines 39–43](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/Resources/ResourceData.cs#L39-L43); [RpfManager.cs, lines 35–79](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/RpfManager.cs#L35-L79)

The separate Gen9 shader/material-parameter mapping is `ShadersGen9Conversion.xml`. Enhanced drawable shader parsing calls `EnsureShadersGen9ConversionData`, which loads this file beside Core. That path is absent from the selected YMAP/YTYP/YBN and Bounds readers; it is not an additional prerequisite for this collision-only import. It would become a dependency if I added those drawable/shader paths. Collision material identifiers also do not establish measured acoustic absorption. [Drawable.cs, lines 663–667](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/Resources/Drawable.cs#L663-L667); [GameFileCache.cs, lines 5763–5775](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/GameFileCache.cs#L5763-L5775)

Upstream Core targets `netstandard2.0` and references SharpDX and SharpDX.Mathematics 4.2.0. My Windows worker instead compiles the full 114-file Core source closure with its pinned managed libraries and framework references. This research found no additional native decryption DLL or GUI dependency for that closure. The shader XML and `strings.txt` are upstream output assets with separate uses; neither supplies NG state. ## Archive identity and the supported world subset

Core decrypts each directory with its original archive leaf filename and `(uint)FileSize`. My bounded table stream must retain the entire logical archive length even though it reads only a prefix. A nested archive uses its member filename and its own extent/decoded length, not its outer archive's name or length. Encrypted binary members use their member name and uncompressed length. Lowercased catalogue paths and staged filenames cannot replace these cryptographic identities. [RpfFile.cs, lines 60–75, 154–170 and 547–555](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/RpfFile.cs#L60-L75)

| Input | My current bounded provider support |
| --- | --- |
| RPF | RPF7 NONE/OPEN, NG and AES through actual Core; unknown tags fail. Genuine Enhanced applicability still needs an approved run. |
