# WORLD-10: my minimal CodeWalker.Core API boundary

I can use CodeWalker.Core in my completely free, open-source project without copying CodeWalker implementation, and I may redistribute Core with necessary dependencies under the permission I received from dexyfex. That permission excludes the complete application. It does not establish permission for my WORLD08/09 modified Core, proprietary bootstrap material, or every third-party component embedded in a vendor binary.

Codex implemented and tested a RichAudio-owned, explicit-memory resource adapter. **A qualified, unmodified Enhanced-capable Core binary has not been acquired or tested. Product packaging and automatic genuine-world initialization remain blocked.** My source-based WORLD08/09 research, original fixtures and historical results remain intact.

## What Codex actually implemented

[`CodeWalkerPublicApiAdapter10.cs`](../src/acoustics/world/CodeWalkerPublicApiAdapter10.cs) reuses my existing bounded compressed-RSC7/page/Meta boundary and geometry DTO normalization. Its decode route uses public Core APIs. It has no archive discovery, executable scan, implicit bootstrap loader, private reflection call or adapted upstream implementation. Preparation stays outside the audio callback and critical GTA fiber.

The adapter accepts exact resource bytes, their expected SHA-256, an explicit source authority, a caller-bound parser SHA-256 and the Gen9 selection. It preserves my existing YMAP/YTYP/YBN geometry and transform fields, serializes/restores the existing process-global Gen9 guard, and rejects an output above 1 MiB. The byte/page/Meta checks are unchanged. The output cap is checked after normalization; it is not a hard memory-allocation or process-time guarantee. Native process memory/time containment remains a separate genuine-input prerequisite.

The adapter deliberately reports binary provenance as requiring independent audit. Caller-provided parser hashes, fixture success and the admission profile's source revision do not authenticate an actual vendor binary. Its envelope keeps `standardBinaryQualified`, `distributionQualified` and `genuineEnhancedGeometryQualified` false. The predecessor normalizer's build-origin label is replaced only in this new envelope; original historical output is unchanged.

`Audit-CodeWalkerApi10.ps1` examines CLR names, referenced assemblies, framework metadata, MVIDs, resource **names**, lengths and software digests using ReflectionOnly loading in a fresh Windows PowerShell process. It neither executes Core initializers nor reads resource values or method bodies. The current tool admits only exact hash-pinned research software staged under this checkout's `.local`; it cannot qualify an arbitrary supplied/game DLL. `Test-CodeWalkerPublicApi10.ps1` compiles only RichAudio-owned adapter files and runs the separate original-fixture probe. No new Core is built.

## Binary provenance and the bootstrap conflict

The pinned [Core project](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/CodeWalker.Core.csproj) targets `netstandard2.0`, references SharpDX and SharpDX.Mathematics 4.2.0, and declares `Resources/magic.dat`. Its [resource accessor](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/Properties/Resources.Designer.cs) expects a managed byte-array resource named `magic`. This is a concrete conflict risk with my requirement to ship no proprietary bootstrap data. **It is not proof of the contents of an uninspected DLL.** Codex did not fetch that data, any `.resx`, a complete app archive or a public Core package payload. Removing or repackaging embedded data would create a modified binary and is not an approved substitute for an authenticated vendor artifact.

The official [GitHub releases page](https://github.com/dexyfex/CodeWalker/releases) had no releases; its release metadata API returned an empty list. [NuGet's CodeWalker.Core page](https://www.nuget.org/packages/CodeWalker.Core/1.0.3) lists 1.0.3, published in August 2024 and owned by `Ancapo`. The project link and dexyfex attribution do not authenticate that package as an official current binary; its publication date also does not establish Enhanced support. Codex inspected package metadata only and did not download it. No official Core-only download, hash, matching build revision or secret-free provenance was established by this research.

My release gate therefore needs an independently authenticated, unmodified vendor Core artifact whose exact metadata and proprietary-data status have been reviewed, with the applicable permission and notices. Metadata-only resource-name inspection can detect a suspect resource; it cannot prove that every possible embedded secret is absent. A reviewed bootstrap mechanism must establish its separate provenance and permitted acquisition/use. These requirements remain unsatisfied.
