# NFSgauge telemetry review

Reviewed 2026-11-01. The supplied NFSgauge 2.7.0 archive is useful implementation evidence, but it does not establish a calibrated physical RPM counter or a validated provider for GTA V Enhanced 1.0.1158.16. No archive binary was executed, loaded, installed, or deployed.

| Question | Finding |
| --- | --- |
| ScriptHookVDotNet dependency? | The supplied `NFSgauge.asi` is a native AMD64 PE DLL with no CLR metadata. Its imports directly reference `ScriptHookV.dll`, including `nativeInit`, `nativePush64`, `nativeCall`, script registration/waiting, and texture functions. The archive contains no managed DLL. |
| Advertised compatibility? | The author lists release 2.7.0 on October 3, 2026, and game 1.0.3889.0 support; an author comment specifies testing on that version, non-Steam. These statements do not establish support for Enhanced 1.0.1158.16. [Author's release page](https://www.gta5-mods.com/scripts/nfsgauge-rpm-gear-speedometer). |
| Source provenance? | XMOD links the `lichguard/GTA-V-MOD-Project---NFSgauge` repository in the release-page comments. Reviewed immutable commit: `ad1a94f1abf998d625633451837d5f4db9dd5ceb`. Its README describes a reconstructed C++ implementation; a reproducible match to the supplied ASI has not been established. [Pinned README](https://github.com/lichguard/GTA-V-MOD-Project---NFSgauge/blob/ad1a94f1abf998d625633451837d5f4db9dd5ceb/README.md). |
| Actual source acquisition method? | `GtaRuntime::capture` reads `memory_.rpm(vehicle_)`. `VehicleMemory` scans the executable for signatures, resolves the entity pool and RPM field offset, then dereferences a vehicle float. This is an executable-dependent memory field, rather than a documented RPM native or SHVDotNet property. [Runtime](https://github.com/lichguard/GTA-V-MOD-Project---NFSgauge/blob/ad1a94f1abf998d625633451837d5f4db9dd5ceb/NativeSpeedo/gta_runtime.cpp), [memory reader](https://github.com/lichguard/GTA-V-MOD-Project---NFSgauge/blob/ad1a94f1abf998d625633451837d5f4db9dd5ceb/NativeSpeedo/vehicle_memory.cpp). |
| Quantity and display scaling? | The source treats the sample as a normalized fraction: it clamps to 0..1, uses zero when engine-off, multiplies by 100 for a damped needle, and applies skin-specific rotation. A painted dial or its 0..9 label therefore does not establish revolutions per minute. [Presentation implementation](https://github.com/lichguard/GTA-V-MOD-Project---NFSgauge/blob/ad1a94f1abf998d625633451837d5f4db9dd5ceb/NativeSpeedo/domain.cpp#L86-L132). |
| Failure semantics? | Missing pool/field resolution can produce `0.0f`; zero does not distinguish unavailable telemetry from an engine state. A matching signature alone cannot validate the field on another executable. Source notes explicitly retain that limitation and say in-game behavior and texture calibration were not exercised. [Pinned implementation notes](https://github.com/lichguard/GTA-V-MOD-Project---NFSgauge/blob/ad1a94f1abf998d625633451837d5f4db9dd5ceb/REWRITE_NOTES.md). |

Static byte inspection found the source's RPM signature once in the supplied ASI. That supports the relationship but does not prove equivalent control flow, correct field resolution, or the exact presentation behavior of this binary. No physical RPM conversion, per-vehicle idle/redline calibration, or Enhanced compatibility evidence was established.

For RichAudio, retain the existing sourced SHV native probe path. This archive supplies no verified replacement contract that would justify adding memory scanning or another runtime. The current probe's idle observation remains separate from physical RPM calibration and multi-state provider validation. No NFSgauge code, offsets, assets, or runtime dependency were integrated.
