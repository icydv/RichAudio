# ACOUSTIC-WORLD-04.2: my one-building export route

My practical second route is a small, explicitly supplied export of one genuine Enhanced building. Codex researched public documentation and named source functions, then exercised the pinned public CodeWalker library on original authored binary fixtures. No interactive CodeWalker/Blender exporter was launched and no installation was inspected. I have not supplied a genuine export yet. This guide describes what a future export must preserve, not an approved installed-game operation or actual compatibility result.

## Tool and format evidence

CodeWalker commit `485d56bec00262ed7fa472261cce7bbc6202b96e` has a Gen9-aware key-loading call in [`ExploreForm`](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker/ExploreForm.cs#L180-L200). Its [selected-file XML path](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker/ExploreForm.cs#L1504-L1530) reads the resource and invokes `MetaXml`; the [dispatcher](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/MetaTypes/MetaXml.cs#L15-L80) includes YMAP, YTYP and YBN. These are concrete source capabilities. A release label or that source commit alone does not identify a downloaded executable or prove its output on my Enhanced build.

The official [Sollumz format table](https://docs.sollumz.org/features) lists `.ymap.xml`, `.ytyp.xml` and `.ybn.xml`, including MLO archetype editing. Its [v2.9.0 release](https://github.com/Sollumz/Sollumz/releases/tag/v2.9.0) describes a changed map workflow and LOD handling. The older [2.6 documentation](https://docs.sollumz.org/2.6/features) explicitly requires CodeWalker XML conversion before binary import. I must bind the actual version and pipeline used; those old instructions are not a qualification of every current binary importer. Sollumz can help inspect supplied XML in Blender, but my first evidence should retain the direct CodeWalker export before any Blender edit or re-export.

The pinned [CodeWalker README](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/README.md) distinguishes placement YMAP, archetype YTYP and bounds YBN, and documents Explorer mode. Starting a normal tool can still load keys or inventory archives. Neither Explorer mode nor leaving edit mode disabled creates my exact resource-access allowlist. No interactive CodeWalker/Blender launch, install discovery, asset-library build, directory import or export of installed resources is authorized here.

Codex's [original-format XML oracle](../tools/Test-CodeWalkerXml042.ps1) executes actual pinned library export/parser/builder APIs: **18 XML exports, 36 selected static DTO roundtrips and five XML rejection controls pass** across original Legacy/Gen9 writer fixtures. The [test code](../tests/CodeWalkerXml042.cs) covers ordinary stored rotation, nonuniform scale, composite collision transforms, geometry centers, triangles and packed materials. The default XML convenience writers select `gen9=false`; explicit builder calls test each writer mode separately. Comparisons cover the supported static DTO fields, not every format field or byte-identical output. An inconsistent authored bound initially saturated a vertex during binary encoding; that failure is retained, and the fixture was corrected without changing the comparison tolerance. These library checks do not qualify a genuine XML/RSC7 decoder, arbitrary native parser containment or my Enhanced installation, and they supply no runtime activation or acoustic proof.

## Smallest useful supplied set

After a separately approved export operation, or from an existing export I am entitled to supply, I would stage these privately outside the installation:

1. One unedited `.ymap.xml` with the selected entity's stable index/identity and complete position, rotation, scale and activation fields.
2. Its relevant `.ytyp.xml` with the exact archetype/hash and physics dictionary relationship. A matching basename is not dependency evidence.
3. The corresponding external `.ybn.xml` with complete collision hierarchy, vertices, triangles, material indices, geometry centers and composite matrices. World collision can reside in a world YBN; an archetype can instead reference local collision or bounds embedded in a drawable. There is no universal YMAP-to-YTYP-to-same-name-YBN chain. My first candidate requires an actually identified external YBN association. Embedded YDR bounds, MLO/composite-instance associations and unsupported bound shapes need a separately reviewed extension. If the required collision is elsewhere or cannot be associated, stop and revise the allowlist rather than fetching it automatically.
4. One future `RichAudioSuppliedExportMetadata042` metadata envelope, at most 256 KiB, naming those three exact files, sizes and digests. Its `buildingContract` contains the unchanged `RichAudioSuppliedBuilding042` structure; its separate `exportProvenance` contains exporter version/executable/settings, source edition/build/origin, permission declarations/evidence, three artifact bindings and transformations. The [proposal specifies its fields](ACOUSTIC_WORLD_042_READ_ONLY_PROPOSALS.md#path-b0-one-export-metadata-envelope-first). Unknown permissions or identities stay unqualified.

No YDR, YTD, textures, audio, executable, whole archive or unrelated dependencies are in this first set. The first subset requires direct unedited exports and an empty transformations list. If removing unrelated XML entities is necessary, retain the original privately and propose a deterministic, reviewed subset transformation under a revised scope. A hand-authored replacement cannot become genuine-resource evidence by changing its label. The [proposal](ACOUSTIC_WORLD_042_READ_ONLY_PROPOSALS.md) first admits only the metadata envelope, then separately gates exact resource reads and a qualified decoder.

The current fixture validator does not accept this new envelope or arbitrary provenance fields, and it cannot certify a genuine archive owner from its XML member identity. The future metadata validator is unimplemented. It must cross-bind each original raw archive/member (`.ymap`, `.ytyp`, `.ybn`) to the separately named supplied XML file and later decoded building contract; basename matching is insufficient. No current fixture guard is relaxed, and declarations of exporter identity or permission do not authenticate themselves.

## Position and collision checks

For ordinary `CEntityDef`, the pinned [CodeWalker constructor](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/FileTypes/YmapFile.cs#L1738-L1796) uses position, `(scaleXY, scaleXY, scaleZ)` and the inverse stored quaternion. `CMloInstanceDef` uses a distinct rotation convention and MLO children compose with their parent. Sollumz at `f12e76891a3b199ef9c380eab11ef578a736b5cf` [exports the same ordinary/MLO distinction](https://github.com/Sollumz/Sollumz/blob/f12e76891a3b199ef9c380eab11ef578a736b5cf/ymap/ymapexport.py#L85-L96). A generic quaternion interpretation is insufficient.

CodeWalker's [bound vertex calculation](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/CodeWalker.Core/GameFiles/Resources/Bounds.cs#L1401-L1414) adds `GeometryCenter` before the bound transform. The pinned [Sollumz importer](https://github.com/Sollumz/Sollumz/blob/f12e76891a3b199ef9c380eab11ef578a736b5cf/ybn/ybnimport.py#L80-L87) transposes the serialized composite matrix for its Blender representation. That conversion is not an extra transform to apply after CodeWalker conventions have already been interpreted.

The sidecar must state whether the selected YBN is already in world coordinates or is archetype-local. Entity placement applies exactly once only in the latter case. Unknown frames, unsupported bound primitives, missing parents, ambiguous hash collisions or an unresolved collision association remain unqualified. At least three non-collinear local/world control correspondences, declared units, their independent measurement source and tolerances must check translation, rotation and scale. A self-generated expected answer or visually plausible overlay cannot independently calibrate the export.

Effective base/DLC/custom-map precedence and IPL/interior/entity-set activation need separate evidence. A tool's displayed DLC selection is recorded as tool state, not live Story Mode state. The [current Sollumz map documentation](https://docs.sollumz.org/documentation/maps) explicitly distinguishes scripted maps and export containers. MLO rooms/portals, doors/windows and changing runtime activation must retain unknown state unless supplied and validated. No export route alone proves indoor propagation, connectivity or acoustic material coefficients.

My new supplied-building contract may validate an original authored fixture and explicit DTO packet chain. Existing importers still reject real authority. No real XML or RSC7 decoder has been qualified by that fixture. A genuine export still needs a separately reviewed decoder, a real-resource promotion adapter and provenance/calibration evidence before it can qualify any installed building. Real package metadata remains blocked; it cannot be relabelled as a fixture.

Tool licensing remains separate from asset permissions. CodeWalker's [source notice](https://github.com/dexyfex/CodeWalker/blob/485d56bec00262ed7fa472261cce7bbc6202b96e/Readme_Src.txt) says educational purposes; the inspected Sollumz tree contains a [GPLv3 license](https://github.com/Sollumz/Sollumz/blob/f12e76891a3b199ef9c380eab11ef578a736b5cf/LICENSE). Neither notice by itself grants redistribution rights for a game export. Proprietary XML and private provenance stay out of GitHub.
