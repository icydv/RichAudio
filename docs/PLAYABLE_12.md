# PLAYABLE-12: functional RPH compatibility and passive SHV handoff

**GO for approval of the exact passive candidate below. Not deployed, launched, live-qualified or audible.** The owner has explicitly removed third-party RPH distribution authentication from RichAudio's responsibilities. This is the operational policy, not a diagnostic exception. No maintainer authentication or API hash whitelist is required before integration can proceed.

Development started at `8c06c46ee0c1925d93692fbac6672116cd7f8537` on `feature/playable-01`, after inspecting the real working tree. PLAYABLE-10 measured different launcher/API bytes with the same FileVersion. PLAYABLE-09 rejected before source attachment. Those findings neither demonstrate API incompatibility nor invalidate the accepted PLAYABLE-08 Bati signal. PLAYABLE-12 changes RichAudio's authored policy and proceeds to test functional behaviour; it makes no new claim about RPH distribution origin.

The operational entry now checks the actual typed RPH contracts it uses: loaded type context, required getters/methods, value layouts and native-dispatch signatures. It does not compare launcher/API bytes, require a known API digest, or require an API path/version whitelist. API location, hash, version and module metadata are best-effort private diagnostics only. Harmless compiled fixtures with unrelated same-version bytes, an unknown version and an empty API location/hash/version are admitted. Missing/incompatible required contracts fail before module attachment/Open. Actual story, vehicle and camera operations continue to reject exceptions, invalid data and context changes.

The old policy was also removed from shared scope matching, module admission and the lease. Module attachment retains exactly five artifact pins: reviewed game, SHV, loader, our producer and our caller. The actual API/launcher is not a sixth runtime distribution pin. Historical RPH metadata carriers remain for compatibility with preserved evidence/fixtures, but are not scope or admission operands. The new strict lease has 21 fields, explicitly selects `runtimePolicy=functional-compatibility`, and has no `rphPath`, `rphSha256` or `rphVersion` expectation. Old profiles/fields, unknown/duplicate fields and activation opt-ins still reject. Both development and normal operational handoff builds use this same policy; there is no alternate provenance opt-in.

The passive lifecycle has a non-inlined call boundary inside an outer catch so a missing method/type during JIT can fail safely before the handoff's own try begins. The outer failure path uses BCL stderr rather than another RPH method. Loader failures that prevent entry execution remain an unobserved plugin outcome, not proof of successful diagnostics or cleanup. The standalone historical PLAYABLE-10 provenance core is excluded from the new operational assembly.

No native code or producer bytes changed. The native `0xF9DDA40BC293A61E` call remains in SHV's script context. All existing process-creation, module/export/ABI, caller and session ownership checks remain. No SHV/RPH handle equality, memory scan, guessed offset, speed-derived engine value, alternate framework or RPH revolution-getter fallback was added.

The retained path is attachment → metadata → owned Open → measured clock anchors → operator arm → independent Bati correspondence → BEGIN → raw records → shared validator/expiry consumer → existing gameplay adapter/codec → bounded private evidence. Functional compatibility diagnostics are journalled before Open. Journal failure still prevents a valid qualification. The normal product's audio/menu lifecycle is not reachable from this passive profile.

Independent RPH/SHV player, ped, driver and motorcycle observations, read-only pool-counter/address checks, exact raw float32 promotion, sequence ordering, measured clock uncertainty, 250 ms freshness/continuity/expiry, replay rejection, autonomous missing-stream retirement and no-rebind retirement remain unchanged. Clock calibration still needs at least three ordered anchors spanning 250 ms, at most 4 ms anchor width and 100 ppm uncertainty. The read-only strategy still excludes a fully unobserved counter wrap plus address-reuse cycle. These ownership checks are not protection against equally privileged malicious code inside the process.
