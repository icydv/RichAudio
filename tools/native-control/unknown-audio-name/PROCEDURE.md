# Unknown vehicle audio name

I listen to one disposable stock ADDER pair in offline Story Mode. Codex operates the experiment. The question is whether A's identifiable, running idle disappears after asking SHVDNE for a deliberately unknown audio game object. This trial uses the vehicle's ForceUseAudioGameObject(string) wrapper. In the pinned SDK it passes the handle and name to FORCE_USE_AUDIO_GAME_OBJECT (0x4F0C413926060B38). The maintainer suggested an invalid dictionary hash and mentioned reverting in an abort callback. This tests the named-object interpretation. A direct dictionary-field write, the internal lookup result and recovery through a stalled script remain untested.

## Interpretations and stopping rules

- A's identifiable sustained idle disappears with A still running, B remains audible and normal, and the same cue returns on the same A after ADDER: reversible per-vehicle loss of the measured idle cue under these conditions. A surviving horn narrows the observed effect to the tested cues. An absent horn that also returns demonstrates broader audible impact.
- A remains audible or changes only briefly: report persistence, timbre or transition in the corresponding interval. A continuous cue cannot support sustained muting.
- B changes too, A and B cannot be separated, capture or state fails, or release is uncertain: retain the observation and report the unresolved attribution or return. Mixed loudness cannot settle it.
- The void native return establishes only dispatch. Even reversible idle loss leaves the internal cause open. Arbitrary prior/modded profiles, loaded driving or high-RPM audio, and independent recovery after script failure are outside the result.

Reserve self, unknown and release once each. B receives zero audio assignments. Emergency release substitutes for the scheduled final ADDER. An untouched A requires no release.
